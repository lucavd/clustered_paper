# Decisione

1. Il repository di lavoro `lucavd/MMM` resta privato: i dati individuali della coorte neonatale (`data_raw/LURID.sav`, `data_raw/LURID.xlsx`, `ARTICOLO 2026/LURID_bis/lurid_patient.rds`) sono in tutti i rami e nella storia dal commit 890e36a (2024-11-18). La storia non si riscrive.
2. Il codice del paper si pubblica in `https://github.com/lucavd/clustered_paper` e il pacchetto in `https://github.com/lucavd/fewclust`, repository creati dal PI. Le loro storie partono vuote e ricevono un commit per ogni sincronizzazione con `tools/public_sync.sh` ("Sync from private repository, commit <hash>"), con un elenco di percorsi ammessi (`PATHS_PAPER` nello script; per il pacchetto la cartella `fewclust/` del ramo package).
3. Prima di ogni commit pubblico lo script controlla che non ci siano file della coorte, righe con le variabili dei pazienti, credenziali o file oltre 50 MB; se un controllo fallisce non pubblica. Le credenziali Telegram scritte negli script dei run originali si sostituiscono con variabili d'ambiente nella copia pubblica.
4. I risultati per replicato (`results_full/` e i file per replicato di `results_v4/` letti dalla catena delle tabelle, circa 10 GB) vanno su Zenodo come dataset separato, con un proprio DOI; il README del repository pubblico lo dice.
5. Il DOI del codice nasce da un rilascio GitHub di `clustered_paper` collegato a Zenodo, come previsto da [Codice pubblico alla sottomissione, con DOI (D-06)](D-06.md).

# Motivazione

Zenodo archivia automaticamente solo repository GitHub pubblici, e il paper dichiara che i dati della coorte non sono pubblici. Un repository copia con un elenco di percorsi ammessi tiene separati il lavoro e la pubblicazione senza riscrivere la storia, quindi i commit citati nei documenti del progetto restano validi. I risultati per replicato superano i limiti di GitHub ma stanno nel limite di Zenodo (50 GB per record).
